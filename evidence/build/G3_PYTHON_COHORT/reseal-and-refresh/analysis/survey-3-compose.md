## 0. One-paragraph model of the pipeline

`cli.py` (the `present` flow, ~L2560-2860) clones/snapshots (S1), decides processability, executes README examples + a build and extracts `facts.json` (S2, with live HTTP), then `repair/rounds.py::run_round` (L326-597) runs S3 investigation -> S4 reconciliation (batched) -> S5 planning -> S6 authoring (per section/slot) -> S7 render -> S8 coherence (batched, then re-render) -> S9 validation -> S10 review; `run_transaction` (L1059) loops repair rounds (S11) and `bundle/seal.py` seals (S12). Every LLM call goes through `core/llm/jobs.py::run_job`, keyed by `canonical_hash({"prompt_sha256", "payload"})` where the payload contains the model, the fully rendered system+user messages (packet + schema embedded), sampling and the (call-)schema (jobs.py L502-518, L556). The check functions (`reconcile_checks`, `plan_checks`, `unit_checks`, ...) are NOT in the hash but DO run on every cache reuse and normalise the stored output in place (jobs.py L557-571, the docstring at L536-540) - that is the single most important mechanism for Q3.

## 3. Q2 - What can be re-run offline with zero LLM calls from sealed artifacts

### 3.1 Deterministic functions of the sealed artifacts
1. **S7 render (and the whole README.md)**: `composition/renderer.py::render_readme(entry, facts, plan, units, dispositions)` (L1084) is a pure function (docstring L1-9; no I/O, no clock, no env, no network - I grepped the module: the only I/O is `write_text`). Patch: `render_patch(original, rendered)`; line budget: `line_counts`.
   - **Existing precedent**: `bundle/reproducibility.py::reproducible_repositories` (L63) does exactly this per bundle: `_load_facts(bundle/"facts.json")` (L34), `find_entry(load_registry(root/"data"/"registry.json"), facts.repository)`, then `render_readme(entry, facts, _read(bundle,"plan.json"), _read(bundle,"content_units.json"), _read(bundle,"dispositions.json"))` and byte-compares with `README.md`. It must call `known_ecosystems()` first so `core.ecosystems.spec_for` knows the ecosystem specs.
   - Extra inputs needed: **`data/registry.json`** (for the `RegistryEntry`: name, ecosystem, repository, family, platform) and nothing else - **no clone, no env vars, no network, no gateway**. (`product_name` is derived from `entry.name`; the banner/Enterprise/CI badge/licence all come from facts.)
   - Note the sealed `content_units.json` is the *final, post-coherence* unit set, so it re-renders to the sealed README (modulo code drift - see 3.3).
2. **S8 mechanics**: `apply_coherence`, `coherence_batches`, `coherence_batch_units`, `coherence_content_loss_errors` / `recover_coherence_content_loss` are pure, but they need the *raw coherence reply* (only in `raw_calls.json` for 5/30 bundles or in a local `runs/.../calls/`).
3. **The check/normalisation functions of S3-S6** are pure and can be re-run on a stored output without a call - they are exactly what `run_job` re-applies on every cache reuse:
   - S4: `reconciliation/dispositions.py::reconcile_checks(output, facts_batch, policy)` (L955) = `normalize` (L509, mutates in place) + `placement_errors` (L872); then `merge_dispositions` (L284) and `coordinate_neighbor_promises(dispositions, facts)` (L774). Needs `facts.json`; the per-batch outputs are in `raw_calls.json` (for the 5 bundles that have it; the merged, post-fold result is `dispositions.json`).
   - S5: `planning.py::plan_checks(output, facts, policy, dispositions, ecosystem)` (L837; mutates the plan *and* the dispositions dict), plus `section_conditions` (L143). Input: `plan.json` + `dispositions.json` + `facts.json` + `entry.ecosystem`.
   - S6: `authoring.py::authoring_tasks(entry, facts, investigation, dispositions, plan)` (L997) rebuilds every `SectionTask` (packet, slots, closed fact sets) from `investigation.json`, `dispositions.json`, `plan.json`, `facts.json`; `unit_checks(output, task, facts, name)` (L1722) can then be run on `{"units": [that task's units from content_units.json], "omitted": [...]}`. Caveat: the sealed units are *already normalised* (backticks stripped, echoed ids stripped, repeated slots merged) and *post-coherence*; the model's raw pre-normalisation reply is only in the gitignored `runs/transactions/<repo>/<rev>/calls/` store. So "re-run normalisation from a sealed bundle" really means "re-verify idempotence/acceptance of the sealed result under new rules", not "re-normalise the raw model text".
4. **Packet/schema builders** (`investigation_packet/schema`, `reconciliation_packet/schema/batches`, `planning_packet/schema`, `authoring_tasks/authoring_schema`, `coherence_packet/schema`, `review_packet`) plus `core/llm/jobs.py::request_hash(manifest, packet, call_schema, model=)` (L502) let you compute, offline, the exact cache key every stage would use today. `rounds.py` L412-424 already does this for S6 (`request_hash` + `reconstructed_task_output`).
5. **Seeding** (what `present` already does without runs/): `bundle/seal.py::seed_call_store` (L635; investigation/dispositions/plan, only if the ledger has exactly one success for that job), `seed_additional_calls` (L690; everything in `raw_calls.json`), `authoring.py::reconstructed_task_output` (L2277; non-batch S6 tasks from `content_units.json`, guarded by `_reconstruction_lineage_holds` L2241 = prompt sha + each cited fact's `canonical_hash`).

### 3.2 What is NOT reproducible offline from the bundle

The bundle holds `README.patch` (the original is recoverable by reverse-applying the patch to `README.md`) but **not `tree.json`**; I did not verify which checks need the tree vs. the clone (validation is outside this slice).
- S10 request hash: `review_packet` (`review/independent/review.py` L268) contains `original_readme` (recoverable), `facts`, `plan`, **`dispositions` as mutated in memory** (see 6.3) and the validation checks' `details`/`advisory` - the sealed `dispositions.json` may not equal what the packet saw.

### 3.3 Important finding: the sealed corpus is already stale with respect to the renderer

## 4. Q3 - What changes which request hash

Mechanics (jobs.py): `request_sha256 = canonical_hash({"prompt_sha256": sha256(whole prompt YAML text), "payload": {"model", "messages"[system = prompt system + schema_preface + JSON of the *call* schema; user = template with the JSON-rendered packet], "temperature", "max_tokens", "response_format"{json_schema = call schema}, "seed"}})` (jobs.py L206-278, L556). The model is the *effective* model (core/llm/fallback.py selection). On a cache hit the stored output is re-parsed with the manifest's **static** schema + binding + the job's `checks` (NOT `call_schema`) and written back if the checks changed it (L557-571); if the checks no longer accept it the entry is logged `cache_stale` and a live call is made under the same key (L572-596).

Chain of dependence (each packet embeds the previous accepted outputs): facts -> S3 -> (S3 output) -> S4 -> (dispositions after fold) -> S5 -> (plan after `plan_checks`) -> S6 -> (units) -> render -> S8 -> (units+README) -> S9 -> S10.

### (a) The renderer (`composition/renderer.py` and anything it calls: `placement.py`, `terminology.py`, `identity.py`, `components/ecosystems.py`, `core/ecosystems.py`)
- **No change** to S3, S4, S5, S6 request hashes: their packets/schemas are built from facts, investigation, dispositions, plan, `authoring.py` text - never from the renderer.
- **Changes S8** (every coherence batch): `coherence_packet` puts the whole `rendered_document` in the packet (coherence.py `coherence_packet`; rounds.py L460). Batch k>1 also depends on the re-render after batch k-1 revised something (L491), so the whole S8 chain re-keys.
- **Changes S10** (every read, incl. second/third): `review_packet` carries `candidate_readme` (rounds.py L542).
- **Changes S11** repair packets only when a repair runs (they carry `stage_output`/defect, not the README, except the visible-line hint from `line_counts(current.readme)` at S5/BC-07).
- Replayable from cache after a pure renderer change: S3, S4 (all batches), S5, all non-batch and batch S6 tasks. Not replayable: S8, S10 (+ any repair). **But** `reconstructed_task_output`'s content comes from the post-coherence `content_units.json`, see 3.5 below.

### (b) Normalisation / `unit_checks` / `plan_checks` / `normalize` / other `checks=` functions
- The check functions are **not part of the hash**, so S3-S6 keys do not change by editing checks per se. What changes is the *folded output reused* from cache:
  - `unit_checks` (authoring.py L1722) mutates units (strips backticks, echoed fact-ids, merges repeated slots, drops unplanned slots). A rule change that still accepts the stored units but rewrites them differently changes `units` -> **S8 and S10 hashes change** (rendered_document / existing_units / candidate_readme), S6 does not. A rule change that rejects a stored unit -> `cache_stale` -> live S6 call (same key).
  - `normalize` / `placement_errors` / `coordinate_neighbor_promises` (dispositions.py) change the dispositions fed to S5, S6, S8 (via placed units and `_placed_units`) and S10 -> **S5, S6, S8, S10 hashes change** whenever the fold's output differs for that repo (not S3/S4).
  - `plan_checks` (planning.py L837) mutates the plan (composes `sections`, appends backstop examples/links, trims links/hubs) -> **S6, S8, S10 change**, S5 does not.
- Caveat: `authoring.py` also *builds the S6 packets* (`_OBJECTIVES` L395, `section_spellings` L1155, `slot_rendering` L604, `section_selections`, `slot_fact_sets`, `carried_units`), and `canonical_abbreviations` / `allowed_identifiers` are consumed by the renderer. So `NORMALISATION_VERSION` (one constant, one file) covers three different things: packet text (hash-affecting), checks (hash-neutral, output-affecting) and renderer vocabulary. An edit to `_OBJECTIVES` re-keys every S6 call; an edit to `unit_checks` does not.
- `core/llm/binding.py` (`fold_duplicate_units`, `resolve_symbol_ids`; outside slice) also normalises on reuse and is not in any version constant.

### (c) A validator (`validation/registry.py`, BC-xx)
- S3-S8 unaffected (validators run after render).
- **S10 re-keys**: `review_packet` embeds `validation["checks"][*].{id, verdict, causal_stage, details}` and `validation["advisory"]` (review.py L286-297). Any change in a check's wording/threshold that alters `details` for a repo changes that repo's review hash; a change that adds/removes a blocking failure also diverts the loop into repair calls (S11) instead of reaching S10.
- The validator also imports the renderer (`RenderContext`, `renderer_sentences`, `quoted_evidence_elisions`) and `placement`, `link_budget`, `terminology`, `glance` - these are shared authorities (see 6.2).

### (d) A prompt (`prompts/*.yaml`)
- `prompt_sha256` = sha256 of the file text, and the system message is part of the payload, so any byte change (including comments and `route_rationale`) re-keys **every call of that job** (all batches/tasks) and - because the cache is keyed per request - everything downstream whose packet embeds that job's output *only changes if the new output differs*, i.e. for a cached replay the downstream keys are unchanged **until a live call returns different text**. `section_authoring.yaml` is shared by S6 and S8 so one edit re-keys both. Also `max_output_tokens` in the YAML changes `reconciliation_batches` sizing (dispositions.py `_batch_size` L207) and therefore batch ids/packets for S4.
- `seed_call_store` / `reconstructed_task_output` additionally gate on `sealed prompt sha == current` (authoring.py L2241-2275).

### 3.5 (extra) Two replay hazards found while reading
1. **Replay of a bundle whose coherence pass revised something is not zero-call.** `reconstructed_task_output` seeds each non-batch S6 task from the *post-coherence* `content_units.json` (authoring.py L2277-2315; no check of the `coherence` marker). The S8 packet is then built from those units + the render of them, which differs from the pre-coherence packet the original coherence call used, so the raw_calls.json entry keyed by the original coherence hash will not match and S8 (and then S10) would be called live. 16 of the 38 `content_units.json` files in `candidates/` have `coherence.revised` non-empty. This is derived from reading the code; I could not test it end-to-end because no current bundle re-renders byte-identically (3.3). `tests/test_cli.py::test_present_from_an_empty_runs_directory_reuses_a_sealed_bundle` passes with zero calls but its synthetic canary revises nothing (not verified by running it).
2. **Repair rewrites cache entries in place** (rounds.py L979: `tx.store.put(target.request_sha256, job, ..., revised_output)`): after a repair the entry for the *original* request now holds the *repaired* output, and `seed_call_store` re-seeds exactly that pairing from `plan.json`/`dispositions.json` (only for single-success jobs). It is self-consistent but means a stored response is not the model's raw reply, and the `targeted_repair` call itself is in no sealed artifact except `repairs.json`/`calls.jsonl` summaries.

### Probe 3 (local `runs/transactions/*`, stale)
I tried to recompute S3/S4/S5/S6/S8/S10 keys for the 8 newest local transactions with current code and match them to `calls/*.json`: all miss, including S3, which depends only on facts+prompt+packet builder - because the recorded runs predate the current packet/schema code (`investigation_schema` pinning, `SYMBOL_CAP`, etc.; the `repository_investigation` and `presentation_planning` prompt shas still match the ledgers). That empirically confirms that packet/schema-builder edits (not only prompt edits) re-key calls; the local call stores are therefore not usable as a replay cache for the current code.

## 5. Q4 - Template/shell: per-product variation and inherited content

### 5.1 Structure
`SEMANTIC_SHELL` (shell.py L47) has **18** rows (module docstring says "seventeen"): identity, badges, banner, opening, navigation, at_a_glance, key_capabilities, installation, dependencies, quick_start, additional_examples, api_reference, documentation_resources, scope_limitations, development_testing, enterprise_relationship, third_party_notices, license. Owners: D (deterministic from facts: identity, badges, banner, navigation, installation, dependencies, third_party_notices, license), L (opening, key_capabilities, scope_limitations), M (mixed: at_a_glance, quick_start, additional_examples, api_reference, documentation_resources, development_testing, enterprise_relationship). `AUTHORED_SECTIONS` = owner != D and != at_a_glance (authoring.py L53).

### 5.2 Optional sections
- Inclusion is **decided by code, not the LLM**: `section_conditions(facts, policy)` (planning.py L143) evaluates banner (verified illustration+homepage), dependencies (a SUPPORTED dependency fact), quick_start (>=1 SUPPORTED example), additional_examples (>=2), documentation_resources (a non-shell SUPPORTED http(s) link), development_testing (any build_test_asset), enterprise_relationship (live target), third_party_notices (file exists). Required rows are always `True`. `plan_checks` then recomputes additional_examples (from this plan's own quick starts) and documentation_resources (from this plan's links + placements) and writes `plan["sections"]` as `{"section_id","include","reason"}` via `_decision` (L387-396), overriding anything the model sent.
- A second, independent omission layer: `render_readme` drops any included section whose body renders empty (`if not any(line.strip() for line in body): continue`, renderer.py L1100-1102) and Navigation lists only rendered sections (`_rendered_section_ids`). So a *required* section with no supporting fact (e.g. License without a licence file) silently disappears - the check that it should exist is left to the validators.
- `at_a_glance` is hard-wired `True` (planning.py `section_conditions`), and the planning schema removes its `null` variant (planning_schema end), so the diagram is mandatory despite the shell row declaring a condition.

### 5.3 Diagram "archetype"
There is **exactly one** archetype: `_at_a_glance` (renderer.py L887) emits `flowchart TD`, `[StartingPoints subgraph]? --> PRODUCT --> Capabilities subgraph --> [Outputs subgraph]?` with fixed styling-free nodes. Variation is only: Starting Points omitted when the plan has no verified input format; Outputs omitted when no verified output; capabilities in one column (<=5) or two balanced columns (>=6); labels wrapped/shortened by the `glance.py` policy. No per-product diagram type, no choice among archetypes.

### 5.4 Ecosystem-specific text
- Almost all via `core/ecosystems.py::spec_for(entry.ecosystem)` (out of slice): fence language, registry name, `badge()`, `runtime_badge()`, `floor_fact_id/label/declaration`, `clone_and_build/clone_and_run/clone_and_reference`, `verify_command`, `import_pattern`, `source_install_lead`, `example_fences`. Prose vocabulary of registries/hosts lives in `components/ecosystems.py` (`REGISTRY_NAMES`, `HOST_NAMES`).
- Hard-coded Python-isms inside generic renderer code, gated only by fact presence: `_installation` (renderer.py ~L810-835) reads `package:python_versions`/`package:python_requires` and prints "The package supports Python ..." / "`python_requires`". Product-page `PLATFORM_SLUGS` and `products.aspose.org/.com` hosts are hard-coded in `product_pages.py`. Licence prose has two fixed templates (`_MIT_PROSE`, `_GENERIC_PROSE`, and "declared in manifest" variants).
- Per-product *prose* only exists in LLM-owned units (opening, capability sentences, lead-ins, hub sentences, link sentences, scope/limitations, dev summary, Enterprise context). Everything else is a fixed template filled from facts. The Core API table is the one place with a content fallback chain: docstring -> LLM-authored type sentence -> `Defined as `signature`.` -> the generic filler `"Public {kind}."` (renderer.py `_symbol_description`).

### 5.5 Preserving inherited README content (dispositions)
- S3/S4 see the README as `inherited_unit` facts (inherited.py). S4 must give **exactly one** disposition per unit: enforced by the per-batch schema (`unit_id` enum, `minItems=maxItems=len(batch)`, dispositions.py `reconciliation_schema` L335) and by the `unit_ids` binding in core/llm/binding.py.
- Disposition semantics as implemented:
  - `VERIFIED_PRESERVE` / `VERIFIED_MOVE`: the raw markdown is copied **verbatim** after the destination section's composed content (renderer.py end of `_section_body`; inside the `<details>` for collapsible sections), via `placements()`/`placed_texts()`. A unit is *not* rendered if (i) it is a heading/badge row/HTML block or a plan/renderer-owned code block (`owned_elsewhere`), (ii) its cited facts intersect what the plan/renderer already render in that section (`overlap`; `planned_fact_ids` + `renderer_fact_ids` + adjacency rules `_adjacent_rendered_examples` / `_adjacent_section_opening`), or (iii) the destination is excluded (`excluded`; plan_checks then flips it to `DEFER_UNRESOLVED`). Intra-document anchors to headings the candidate will not render are rewritten to plain text (`resolve_intra_document_anchors`).
  - `VERIFIED_REWRITE` / `CORRECT_WITH_EVIDENCE`: nothing is copied; the unit id becomes a citable fact for the destination section's authoring (`_placed_units` in `section_selections`), and links it cites are appended to the plan's `links` by the `_missing_links` backstop. **There is no hard check that the rewritten substance actually appears** - the only enforcement found in the slice's consumers is an *advisory* ("the rewrite no longer names `X`", `validation/registry.py` ~L1917) plus whatever the independent review notices.
  - `SUPERSEDE_REDUNDANT`: deterministic sections supersede (code adds the rendering fact ids). For prose superseded into `development_testing` or `scope_limitations` there is a hard **must-carry** rule: the authored units must cite the unit or list it in `omitted` with a reason (`carried_units`, `carried_unit_errors`, `_CARRY_SECTIONS` authoring.py L523-531) - other sections have no such obligation.
  - `OMIT_UNSUPPORTED` of paragraph/list requires a cited fact (`placement_errors`); `DEFER_UNRESOLVED` is listed for the owner (`validation/deferrals.py`).
  - Code overrides the model in `normalize` (dispositions.py L509-765): e.g. placements into deterministic sections -> `SUPERSEDE_REDUNDANT` + rendering facts; UNRESOLVED example block -> `DEFER_UNRESOLVED`; CONTRADICTED example block -> `OMIT_UNSUPPORTED`; command blocks routed by install/build facts; PRESERVE/MOVE of a unit embedding a CONTRADICTED link -> `VERIFIED_REWRITE`; duplicate-subject placements -> `SUPERSEDE_REDUNDANT`; every symbol a placed unit names is appended to its `fact_ids`. After the merge, `coordinate_neighbor_promises` defers a colon-ending paragraph/list whose immediately following code block was omitted/deferred.
- Net: preservation is verbatim-only for PRESERVE/MOVE; REWRITE/CORRECT rely on the LLM re-authoring from facts with weak downstream verification.

## 6. Q5 - Dead code, duplicated authority, hidden fallbacks, determinism hazards

### 6.1 Dead / unused
- `LINK_BUDGET_VERSION = "1"` (link_budget.py L38): defined, **never referenced** in `src/` or `tests/`; it is not in `dependencies.json`, so a change to the link-budget arithmetic marks no candidate stale.
- `authoring.py::forbidden_text_pattern` (L1489): production-unused (3 test references). Its docstring says it is intentionally not put in the schema; it is a leftover from an abandoned decoder approach.
- `glance.py::label_height`: only tests use it.
- `renderer.py::__all__ = ["renders_verbatim"]` is a re-export shim; `renderer.format_name`, `enterprise_anchor`, `collapse_document_blank_runs` are used only in-module (+tests) but are fine helpers.
- `planning` JSON schema keeps a `sections` property "for re-judging" that code always overwrites (prompts/presentation_planning.yaml; `plan_checks` L893). Harmless but the model is asked to emit/ignore a field.
- `RENDERER_VERSION` is assigned three times in one file (renderer.py L82/L90/L96) - only the last matters; the history is kept as live assignments instead of a comment.

### 6.2 Duplicated / split authority
- Version constants only cover 4 files (test `tests/test_version_bump_discipline.py` `GOVERNED`: renderer.py, authoring.py, review.py, validation/registry.py). **Not governed, yet behaviour-defining for rendered bytes or stored outputs**: `placement.py`, `terminology.py`, `identity.py`, `components/ecosystems.py`, `glance.py`, `link_budget.py`, `policy.py`, `planning.py` (`plan_checks`, `section_conditions`), `dispositions.py` (`normalize`, `coordinate_neighbor_promises`), `dossier.py`, `evidence/facts/*`, plus `core/ecosystems.py`/`core/llm/binding.py`. `SHELL_VERSION` is manual with no AST test. Consequence: editing e.g. `normalize()` or `placement.py` changes sealed output for future runs but flips no `dependencies.json` component, so `status --stale` and the dependency evaluator will not report it. (Policy hash is the only content-addressed one: `canonical_hash(policy_packet())`.)
- `"normalisation"` (NORMALISATION_VERSION) conflates packet text, check/normaliser behaviour and renderer vocabulary (see Q3b); the name suggests `dispositions.normalize` but it governs `authoring.py` only.
- Duplicate definitions (documented as deliberate to avoid import cycles, but they can drift): `_COMMAND_FENCES` in authoring.py L104 and dispositions.py L73; `PLACING` in dispositions.py L59, placement.py (+`PLACED`), validation/registry.py L414 `_PLACING`; `_unit_ordinal` in placement.py and `_UNIT_ORDINAL` (different regex) in dispositions.py; `_product_name(facts)` in planning.py vs `identity.product_name(entry)`; `elide_noncanonical`'s matcher vs validation's; `_ASPOSE_DOMAINS` (planning.py) vs `link_budget.ASPOSE_DOMAINS`; `_SHELL_OWNED_LINKS` (planning.py, 4 ids) vs `_RENDERER_OWNED_LINK_IDS` (dispositions.py, 3 ids) - different sets by design but easy to desync; `anchor()` in renderer.py vs `heading_slug()` in links.py; `renderer_sentences` re-types the API-surface sentences that `_api_reference`/`_documentation_resources` render ("The verified public surface has {n} types.", "It covers all {n} verified public types ...") instead of sharing a function.
- Three unrelated "policy version" values: `composition/policy.py POLICY_VERSION="1"`, `core/state/present_transaction.py POLICY_VERSION="readme-contract-v1-draft"`, `core/authorization/proposal.py CURRENT_POLICY_VERSION="1"`.
- Shell docstring says "seventeen sections"; tuple has eighteen.
- The prompt YAMLs duplicate numeric policy that the code also enforces (e.g. "at most twelve hubs", "16 fact ids", capability 3-8, 28-char labels); `reconciliation` rationale `maxLength 160` is mirrored by `_RATIONALE_MAX_CHARS` in code (a test pins it).

### 6.3 Hidden fallbacks / silent mutations
- `plan_checks` mutates its inputs: it rewrites `plan["sections"]`, appends backstop examples/links, trims Aspose links and duplicate hubs, **and flips excluded placements to `DEFER_UNRESOLVED` in the shared `dispositions` dict** (planning.py L912-920). But `dispositions.json` is written at rounds.py L387, *before* planning runs, so the sealed `dispositions.json` can differ from the dispositions object that authoring, rendering, validation and the review packet used. Rendering is unaffected (an `excluded` placement renders nothing either way) but any offline reconstruction of the S10 packet or of validation from sealed `dispositions.json` can diverge. (Reasoned from code; not demonstrated on a bundle.)
- `unit_checks`, `reconcile_checks`, `coherence_checks` are *normalisers* that mutate model output in place and on every cache reuse; checks are therefore load-bearing for byte-reproducibility.
- Last-resort deterministic "recover" repairs rewrite model output after the second rejection: `recover_planning_output` (dedupe links; auto-splice the first candidate fact into a capability that cites nothing supporting its title), `recover_forbidden_command_units` (replaces `pip install x` / `$ cmd` with canned pointer sentences "the package as documented in the Installation section above"), `_strip_title_verbatim_opening_units`, `recover_visible_line_overage` / `bound_visible_line_overage` (clears optional example plan fields, writes a synthetic `changes[]`), `recover_coherence_content_loss` (reverts units). Each is re-validated by `run_job`, but the accepted text is not what the model returned.
- Fixed fallbacks in the renderer: empty body -> section silently omitted; `"Public {kind}."` filler in the Core API table; `_documentation_resources` always appends an "Open an issue" line; `elide_noncanonical` replaces text with "…" inside quoted docstrings.
- `normalize` overrides model dispositions in ~12 branches (see 5.5); `InvestigationV1` etc. caps (`UNIT_CAP`, `PLANNING_SYMBOL_CAP=1200`, `SYMBOL_CAP` in core/facts.py, `_STATEMENT_FACT_ID_CAP` ...) silently truncate what the model is shown - e.g. only the first 400 heading/paragraph/list units reach S3 and S5.
- `repair_defect` stores the repaired output under the causal stage's *original* request hash (rounds.py L979) - cache entry != raw model reply (Q3 3.5).

### 6.4 Determinism hazards
- **Network/time-dependent facts (S2)**: `product_pages.py` (HTTP 200 lookups), `links.py` (HEAD/GET per README link), registry probes, example/build execution. Same revision can yield different `facts.json` over time; `dependencies.json` records `canonical_hash` of every fact so changes are visible, and `probes.json` is replay-exempt. Everything downstream of S2 is deterministic *given* `facts.json`.
- LLM sampling: temperature 0 + seed 1 but the gateway does not guarantee identical replies (`seal.py::_call_variance` exists to surface multi-response jobs; DECISION_LOG records live non-determinism). Reuse by request hash is what makes runs byte-stable, not the model.
- Set-order ties: `RenderContext.prose` does `for token in sorted(tokens, key=len, reverse=True)` over a `set` (renderer.py ~L250): equal-length tokens iterate in hash-seed order; substitution order only matters for overlapping equal-length tokens, which `identifier_tokens` should not produce, and DECISION_LOG L4701-4710 reports a PYTHONHASHSEED investigation that found no mechanism - low risk, not proven impossible.
- `renderer_sentences(entry, facts, ...)` and validation's `RenderContext(candidate.facts, ...)` use facts in extraction order whereas `render_readme` canonicalises (`facts.canonical()` renderer.py L1100) - order-sensitive helpers (`supported(kind)` iteration, `quoted_evidence_elisions`) can list in a different order than the rendered document (advisory notes order only, as far as I traced).
- `request_hash`/batching depend on `max_output_tokens` (`_batch_size`) and the *model* name; a gateway fallback (`select_models`) or a manifest budget edit silently re-keys S4 and everything else.
- Windows path-length workaround: the call store key is the first 12 hex chars of the request hash (jobs.py `CallStore.path` L145-152) - 48-bit prefix, acceptable but it is a collision-by-design.
- `reconstructed_task_output` (non-batch S6 seeding) trusts content_units.json + dependency hashes instead of the request identity; a batch task is never reconstructed.
