# Review B: 11 source-current candidates with forbidden edition wording

Scope: READ-ONLY. Nothing was written to GitHub or any Aspose repository. Upstream HEAD of every clone equals the sealed revision (verified with `git rev-parse HEAD`), so the clone's README.md is the live upstream README. Per-candidate reviews were done by 11 parallel read-only review agents; the lead (this report) checked the cross-cutting facts below against the repository-presenter source.

## 0. Cross-cutting findings

1. Every one of the 11 candidates is RESEAL_REQUIRED. None can be pushed as-is, and none is safely fixable by a hand edit.
2. Why the wording got through: every bundle was sealed with BC-06 version 3. The current `src/repository_presenter/components/readme/validation/registry.py` (`_edition_substitute_failures`, BC-06 v7) rejects "commercial edition", "paid version", "full version", "on-premise edition" case-insensitively, and any capitalised "Xxx Edition" other than Enterprise. The sealed bundles predate that check. A reseal under the current validator would therefore catch the phrase.
3. The edition sentence is never a one-phrase problem. In every candidate the "adds ..." clause after "commercial edition" cites only identity/package/link facts. Nothing in facts.json supports what is claimed, so the second sentence must be deleted or replaced by a clause traceable to a recorded fact. The only recorded source of "what Enterprise adds" is the live (inherited) README paragraph.
4. Contract row 18 / BC-06 also requires the anchor to open "full-featured" and end "Enterprise Edition". All 11 sealed anchors are `[Aspose.X for Y — Enterprise Edition]` with no "full-featured". Several also use "Cpp" or ".Net" where "C++" or ".NET" is canonical.
5. Quality regression: in all 11 candidates the sealed README is WORSE than the live upstream README. Valuable verified live content was dropped through `SUPERSEDE_REDUNDANT` or `OMIT_UNSUPPORTED` dispositions whose stated rationale ("covered elsewhere" / "no fact supports") is false when checked against the clone. Typical losses: Detailed Member Reference, build/test commands, Additional Examples, dependency versions, docs links. Typical additions: invented audience sentences, wrong target-framework/runtime floors, unsupported counts.
6. Review waivers: in at least 9 of the 11 bundles review.json shows `verdict_as_returned` of REJECT_PRESENTATION or REJECT_FACTUAL that the composition layer converted to ACCEPT by labelling findings `reviewer_scope_defect`. The waived findings were mostly correct.
7. Hand edits break the seal in every case. README.md sha256 is recorded in manifest.json, validation.json and review.json (`readme_sha256`) and bound into README.patch and the BC-11 byte-identical replay. Each agent confirmed the current README matches its manifest hash.
8. Two upstream repos are very large (Page about 1 GB, Words about 560-730 MB working tree) because of tracked test data.
