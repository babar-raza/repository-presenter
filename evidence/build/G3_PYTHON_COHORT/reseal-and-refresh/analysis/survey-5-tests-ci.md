## 1. How a one-product bug fix cascades portfolio-wide (exact rules)

### 1.1 The mechanism
`candidates/<owner>__<name>/<revision>/dependencies.json` records `components` (`normalisation, renderer, reviewer_logic, shell`), `validators` (per `BC-nn` check version), `validator_version`, `prompts` (version+sha256 per job), `policy`, per-fact hashes. `core/candidates.py::stale_candidates()` compares those with the running code's constants. There is no global control-plane hash (enforced by `test_control_plane.py`), but the **version constants are global**, so one bump marks every CURRENT bundle stale.

Measured today (`status --stale`): **30 of 30 sealed bundles are stale**; `candidates: 0/36 current-code reproducible, independently accepted, no-op-proven`. Running code vs. a typical bundle: renderer 24->30, normalisation 12->29, reviewer_logic 12->17, validator_version 3->15, BC-02 3->4, BC-05 1->2, BC-06 3->7, BC-07 7->10, BC-10 4->5, BC-11 1->2 and BC-12 (new, no recorded version). The canary (3D-Python) is at renderer 18 / normalisation 2. So the "N/34" progress unit in AGENTS.md currently reads 0 because the shared code has moved every constant since every bundle was sealed.

### 1.2 Tests that force coordinated edits (the cascade rules)
1. **`tests/test_version_bump_discipline.py`** (AST fingerprint, docstrings/comments stripped). Governed files: `composition/renderer.py` (RENDERER_VERSION), `composition/authoring.py` (NORMALISATION_VERSION), `review/independent/review.py` (REVIEWER_LOGIC_VERSION), `validation/registry.py` (VALIDATOR_VERSION and every `Check(id, version, ...)` literal). Rule: if the AST (minus docstrings) of one of the four files differs between `HEAD~1`->`HEAD`, or between `HEAD` and the working tree, then at least one governed constant in that file must differ. Developer must bump a constant for ANY non-cosmetic edit to those four files, even for a single-product bug. Note: it does not govern `shell` (SHELL version), prompt manifests, `repair/targeted.py` (REPAIR_LOGIC_VERSION), or extractors; those are caught only by dependency hashes, not by this test. Also: the check is weak by design (any constant change satisfies it, not necessarily the right one).
2. **Literal pins that must be hand-edited on every bump** (not generic, just hard-coded expected values):

### 1.5 Net effect, stated plainly
A fix to shared validator/renderer/authoring/review code for one product requires: (a) a governed-constant bump (test_version_bump_discipline) -> (b) literal edits in up to 3 test files -> (c) all 30 bundles read as stale in `status --stale` and the progress unit drops to 0/N -> (d) if bytes change, `KNOWN_BLOCKED_STALE` rows with refs and expiry -> (e) a real reseal through `present` of every bundle (not a bare re-render) before anything can be `current-code reproducible` -> (f) a fresh candidate hash, which invalidates any `ops/proposal-authorizations/<repo>__<hash12>.json` (the propose workflow locates the record by the sealed README's hash) -> (g) a human-merged authorization record and an owner variable before any PR. Plus doc/ledger edits when the bug is in DEFECT_INDEX (register integrity).

### 4.3 Flaky / environment-dependent tests (verified)
1. **Dubious-ownership failure on this machine (reproduced).** The repo (OneDrive of user `prora`) is owned by a foreign SID; the current user is `babar`. The autouse fixture sets `GIT_CONFIG_GLOBAL=<devnull>`, which hides the user's `safe.directory`. Result: `tests/test_path_budget.py::test_every_tracked_path_is_within_budget` FAILS (`git ls-files` exit 128), and `test_version_bump_discipline` skips 8 tests with "git context absent (not a checkout)" (it treats any git failure as no repo). So on this machine the version-bump guard is silently off, even though ci_check/pre-push would appear green only because `run_git`-based skips are not failures. Hosted CI (checkout owner = runner) is unaffected. Skips-as-pass is itself a weakness: depth-1 hosted checkouts always skip the HEAD~1 legs too.
2. **Wall-clock dependence:** `test_sealed_bytes._bundle_param` uses `dt.date.today()`. On **2026-10-19** the 3 entries expiring then (3D-Python canary, Cells-.NET, Slides-Python) stop excusing and the suite goes red; on **2026-11-04** 27 more. The only remedies are a real reseal or a reviewed re-dating within `since+60d`. Also `test_bundle_audits`, `test_governance_consistency` have strict-xfail rows which flip red on an accidental fix.
3. Platform/tool-conditional tests (skipped if toolchain absent, so local and CI differ): C++ (`needs_compiler`, `needs_msvc` Windows-only), TypeScript (`needs_tsc`), `.NET` MAX_PATH (win32), long-path helpers, Windows clone deletion (`test_clone.py` 252/276), `openssl` in `test_install_state`, bash availability for `test_ci_check_output_dir`, `test_check_import_root`, `test_liveness_workflow`, `test_workflow_app_tokens`, `test_workflow_hardening` (also skips when `bash` is a WSL launcher), `test_worktree_scripts` (needs bash and git). Hosted CI is Linux only, so Windows-only logic is never exercised in CI; conversely Linux-only paths are not exercised on the owner's machine.
4. Environment coupling: `PIP_NO_INDEX`/`PIP_NO_BUILD_ISOLATION` mean the suite requires `setuptools>=75` and `wheel` in the venv (earlier 27-worker xdist run failed intermittently without this); the `sealed_canary` fixture installs a package into a throwaway venv (about 20 s). OneDrive: stray `*.pyc.NNNNN` temp files accumulate in `tests/__pycache__` (OneDrive/antivirus locking), and `python_examples.py` carries a "OneDrive workspace-lock" workaround (commit f5a9b27c).
5. Pinned counts that make unrelated tests fragile: `len(plans) >= 30`, `len(sealed) >= 30`, `>= 15` repairs, `dossier widest == {14,11,14}` equality, canary ledger floor, `test_bundle_audits` keys include the 12-char revision.
6. Deterministic/non-flaky by design: no live network in tests (conftest refuses registry, link fetch and LLM client); structural workflow tests parse YAML rather than hitting GitHub.
